Wave 7m - the offline setup: one file, no internet, nothing to install (D-154, AC-188).

A classroom machine may have no internet at all - a locked-down lab, a school network, a laptop on a train. So the project now ships a setup that CARRIES everything it needs with it.

What the inventory found, and it is the reason this is possible at all: THE APP'S NPM DEPENDENCIES ARE NOT NEEDED AT RUNTIME. The app is a static bundle served by nginx - HTML and assets. So the payload never has to carry the npm registry's tarballs, and the offline setup never runs yarn install. And PYTHON IS NOT NEEDED either: the default OCR engine, tesseract, is WebAssembly inside the extension and runs in the extension's own process. Python is only for the optional indra and paddle engines.

What was built:
- installer/offline/build-payload.mjs - downloads the payload (the prebuilt app, the .vsix, the Node MSI for x64 and arm64, the VS Code and VSCodium installers, Python, a Temurin JDK, the VDD Control package and the x86 driver-only package), re-runnable, and writes a manifest.json with every file's SHA-256. It needs the internet only when it is BUILT.
- installer/offline/OfflineSetup.cs - C# 5, compiled by the compiler that ships with Windows, AnyCPU so it runs on ARM64 Windows too. It carries the payload as a resource, extracts it, CHECKS EVERY HASH and refuses a mismatch, installs offline what is missing - asking first, never reaching the internet - and SERVES THE APP WITH NOTHING INSTALLED, using a built-in HttpListener. It also reports the bridge URL the app was baked with, and says so plainly when nothing is listening there yet because the bridge runs inside the editor.
- installer/offline/build-offline-setup.mjs, offline.wsb, run.ps1 - the build and the harness.
- packages/vscode-bridge/tests/offline.test.ts - the AC-188 test.
- docs/OFFLINE.md with the picture from the real run.

GATE 4/4 PASS. rowcheck --all exit 0.

THE PROOF - a Windows Sandbox with NO networking. The .wsb setting alone did NOT take the internet away, so the setup took the network down from inside and then checked every way of asking: DNS did not resolve www.microsoft.com, a TCP connection to 1.1.1.1:443 failed, a TCP connection to 8.8.8.8:53 failed, and an HTTP request to the internet failed. "THE MACHINE IS OFFLINE. Every way of asking the internet failed."

Then, on that offline machine: the payload extracted and every file matched its hash; the app was served from it - GET http://127.0.0.1:4173/ returned 200, it was the app, it loaded the app's own script, and /assets/index-B3WSFxBV.js returned 200 with 2,592,011 bytes; Node.js v24.22.1 was INSTALLED FROM THE PAYLOAD; the other installs were SKIPPED because the test answered no, which is the point - it asks; and with no editor present it said the honest thing - "the extension is in the payload, but no editor is installed to put it in."

The payload carries nine files: app.zip 26.1 MB, the .vsix 23.0 MB, node-v24.22.1-x64.msi 31.8 MB, OpenJDK21U-jdk 195.6 MB, python-3.15.1-amd64.exe 43.4 MB, VDD.Control.25.7.23.zip 67.9 MB, VirtualDisplayDriver-x86.Driver.Only.zip 0.1 MB, vscode-x64-setup.exe 237.3 MB, vscodium-x64-setup.exe 155.1 MB. The executable is 780 MB.

WHAT WAS NOT PROVED, and it cannot be: the virtual display driver install needs administrator rights, a REBOOT and a real display, and a Sandbox has none of those. The driver package is in the payload and the setup offers it with the reboot stated plainly.
