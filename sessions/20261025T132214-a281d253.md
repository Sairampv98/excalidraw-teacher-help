Wave 7n - how to confirm the install is sound, and that the behaviour is the expected one (D-155, AC-189).

The offline setup (wave 7m) is proved to install and to serve the app on a machine with no internet. But a teacher who installs it on ANOTHER machine needs two things this project had not given them: a way to CONFIRM THE INSTALL IS SOUND, and a way to CONFIRM THE BEHAVIOUR IS THE EXPECTED BEHAVIOUR - so that a deviation is obvious and reportable.

installer/verify-install.ps1 - one command. It prints a table, one row per check: check, expected, actual, verdict. The verdict is one of PASS, FAIL or MISSING, and the three mean DIFFERENT things: PASS is it is there and it is right; MISSING is it is not installed, which is often fine because the app itself needs nothing; FAIL is it is there but it is WRONG - a wrong version, a wrong port, a hash that does not match, an editor without the extension in it. That is the one that needs attention.

The checks take their expected values from the code, never from memory: the operating system; Node.js 20 or newer (the repository's own engines); Yarn; VS Code and VSCodium 1.91.0 or newer (the extension's own engines.vscode); the extension listed by whichever editor is installed; the extension's own helpers - capture.ps1, virtual-display.ps1 and ocr_sidecar.py - present in the installed folder; the virtual display driver, with "a reboot is needed" when it is there but not yet attached; the bridge on 47511, which is MISSING rather than FAIL when no editor is running, and the script says why; the app over HTTP, taking the address as an argument and reporting it as NOT CHECKED rather than failing when it is not given; and every file in the payload's manifest.json re-verified against its SHA-256.

The script NEVER installs, changes or removes anything - it only reads and requests. It NEVER crashes because something is missing: every check is guarded and a missing thing is a row in the table, not an exception. It ends with a PASTE-ABLE REPORT - a fenced block the teacher can send back as it is, with the machine's facts, the table and the verdict counts. That block is how a deviation gets reported. It exits 0 when nothing is FAIL and 1 when something is.

docs/VERIFY.md - the feature checklist. Every feature the project has, each with the same four parts: WHAT TO DO (the clicks, in order), YOU SHOULD SEE (the exact words or the exact picture), IF IT IS NOT THAT (what a deviation looks like, and what to check), and SEE IT (the clip that shows it working). The clips are the reference for what correct looks like.

docs/REPORT.md - how to report a deviation: what you did, what you expected and what you actually saw, quoted exactly; which feature; the check report; and the machine. And one line about the token: it is a secret, NEVER include it in a report, and the page does not ask for it.
