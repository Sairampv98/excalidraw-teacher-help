Wave 7l - the setup as one file, the direct install, the container and the guide (D-153, AC-187).

The setup of wave 7k reported what was missing and installed it - but only where a package manager existed, and it had no way to install the editors at all. The end-to-end test in a WINDOWS SANDBOX - a bare Windows with nothing on it, not even winget - showed what that cost: on such a machine the setup could only report. The promise is that it installs what is missing, so it must install everywhere.

Three things now.

ONE FILE. The setup is also an executable, so it can be double-clicked: installer/launcher/SetupLauncher.cs finds the repository, runs installer/setup.ps1 inside it, passes every argument through and waits for it. It is compiled by the C# COMPILER THAT SHIPS WITH WINDOWS (csc.exe), so the project gains no dependency at all, and it is AnyCPU so it runs on ARM64 Windows too. installer/build-setup-exe.mjs builds it and EMBEDS the installer scripts as resources, so the executable carries the setup with it. The launcher is C# 5, because that is what the shipped compiler understands.

WITHOUT A PACKAGE MANAGER. Where winget or brew is there it is used; where neither is there the setup downloads the OFFICIAL installer itself - Node.js from nodejs.org (the latest LTS, for the machine's own architecture), VS Code and VSCodium from their own sites - so a bare machine is set up as well as an ordinary one. The EDITORS themselves are now something the setup installs, because a teacher with neither VS Code nor VSCodium cannot use the bridge. And the plan is made AGAIN after Node is installed, so the things that needed Node - Corepack, the extension's build, the app's dependencies - are done in the SAME run.

A CONTAINER. The app is published as an image: lolking69/excalidraw-classroom:0.1.0, with the bridge's URL baked in at build time and the extension staying on the host.

The end-to-end test also found two defects the gate could not see, because the repository's tsconfig excludes every directory named tests, so packages/vscode-bridge/tests was never type-checked at all: the new test file had five implicit-any type errors, and the container's build context did not contain installer/, so the test's own import could not resolve inside the build. Both are fixed, and the build's heap is now set, because the build inside a container died at Node's default 2 GB while the same build on a developer's machine succeeded.

Also: docs/INSTALL.md - the installation guide, with the pictures, the three ways in, the token, the ARM64 notes, and a table for when something does not work.

GATE 4/4 PASS. rowcheck --all exit 0. 12 tests pass in packages/vscode-bridge/tests/setup.test.ts.

The teeth check: with the fix reverted the AC-187 tests FAIL; with the fix restored they pass again.

The real proof: setup.exe was built with the compiler that ships with Windows and runs; the setup reports everything missing on a bare machine and says what it would install; the container image was built, pushed and served the app over http://127.0.0.1:3000, and pulls anonymously; and the whole flow was run in a Windows Sandbox, which is where the two defects above were found.
