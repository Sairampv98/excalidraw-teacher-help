# next.md - where the work stands and what a new session does next

Private. This file is never mirrored to the public repository (`scripts/public-sync/config.json` denies it).

## How to resume

Open a session in this repository and say: **"Continue: read docs/next.md."**

Then, in this order:

1. Read this file to the end.
2. Run `node .tins/kit/bin/kit.mjs status` (is a session or a gate already running? never kill one).
3. Take the first work item whose status is `NEXT`. Show its SPEC rows to the owner and get a yes **before** building a new feature (a bug the owner reports counts as the yes).
4. When a wave is merged, update this file in the same task: move the item to `DONE` with the merge commit, and write what the next session needs to know. A new session must never have to ask "what was done last?".

Statuses used below: `DONE`, `NEXT`, `HELD` (the owner decided to wait; do not start it), `DROPPED` (the owner removed it; reopen only when asked).

### How a release is made (the runbook, written after 2.2.1; there was none before)

1. **Private `main` is merged, gated and pushed** (`kit close`, `kit merge`; then `git push github main` and `git push origin main`). Each close and each merge runs the ~15 minute gate. A merge on its own does not make anything public, but **a normal `git commit` on `main` runs the hook `public-sync run --hook`, which writes the mirror's commits to the local public clone's `dev` and PUSHES `dev` to the public repository** (the push guard only blocks the very first push of a `dev` that is not on the remote). Check `node scripts/public-sync.mjs scan` before committing on `main`: a task description that names the method (a sentence not in `scripts/public-sync/rewrite-map.json`) stops it, and the fix is a map entry (see `scripts/public-sync/rewrite-map.json`, key = the unmapped paragraph, value = the public wording).
2. **The scrubbed extension**: `node scripts/public-sync/release.mjs --out <folder>` builds the extension (and the old `setup.exe` and the assistant's server), scrubs them and runs the guard. The payloads carry the **scrubbed** `excalidraw-bridge-<version>.vsix`: put it over the one in `node_modules/.cache/gui-payload` and `win7-payload` and update `size` and `sha256` of the `extension` entry in their `manifest.json` (a script that does this is easy to write; keep the old file outside the payload folder: every file in it is embedded).
3. **The release files**: `powershell -File scripts\release\build-release.ps1 -Version <x.y.z> -Out <folder> -Repo Sairampv98/excalidraw-classroom -Cache <full path of node_modules\.cache>` (**pass `-Cache` in full**: `$PSScriptRoot` is empty in the parameter default when it is started from the agent's shell). It needs the folder `gui-payload-vscode` for the small setup. Then `node scripts/release/scan-release.mjs <folder>` (findings in `app.zip` and in the setups' file lists such as `aurora-x-D-2ljcwZ.js` are false positives of a chunk name that looks like an id, and the same `app.zip` is already public; anything else is real).
4. **The public commits** (in a fresh `git worktree add --detach <path> dev` of the public clone: its own working tree is stale on purpose, the mirror writes commits with no checkout, and do not `git reset --hard` it): write the README text (the drafts in `scripts/public-sync/readmes` are behind; the public README is edited by hand), commit it on top of `dev`; make the release commit for `main` with `git commit-tree <dev tip>^{tree} -p <public main> -m <message>` (the tree of `main` is the tree of `dev`); run the guard over the added files and messages; move the refs with `git update-ref` and `git push github-public dev:dev main:main` (fast-forwards, no force).
5. **The release**: write the notes (the 2.2.0 notes are the model: `curl https://api.github.com/repos/Sairampv98/excalidraw-classroom/releases/tags/v2.2.0`), then `node scripts/release/publish-release.mjs --tag vX.Y.Z --notes <file> --dir <folder> --clone <public clone> --expect-main <sha> --check`, and without `--check` to publish (draft, upload, download every file back and compare, then publish; the tag is made by the release).

## Rules that always apply

- **Spec first.** A behaviour change is a SPEC row first (`D-n` decision, `AC-n` acceptance row naming a test file that mentions the id), then the code. Show the rows of a new feature and get a yes before building.
- **One task = one branch + one worktree + one scope**: `node .tins/kit/bin/kit.mjs task new <id> --paths a,b [--overlap-ok]`; link the `node_modules` folders into the worktree with junctions (root, `excalidraw-app`, `packages/excalidraw`, `packages/utils`, `packages/fractional-indexing`, and the `examples` ones); `kit start --task <id>` before every close.
- **The gate**: `GATE_JOBS=2 node .tins/kit/bin/kit.mjs close --note "..."`, then `kit check --base main`. One heavy command at a time; stop throwaway editors and dev servers first; **never kill a running gate or merge**. The timing test `flowLargePresets.test.tsx` (1000 ms) fails when the machine is busy: rerun it alone.
- **Finishing a wave**: preview from the worktree (`node ../node_modules/vite/bin/vite.js --port <port> --strictPort --host 127.0.0.1` from its `excalidraw-app`) with a "what to check" list; after the owner says it works: `kit merge <task>` from the base worktree, stop the preview, push `main` to `github` and `origin`. Public pushes need the owner's explicit go.
- Use **yarn**, not npm; no new dependency without a SPEC decision; **LF line endings, no BOM**; **no secrets** in files or commits; tests must have teeth (check them with deliberate mutations); never edit `sessions/`, `tasks/`, `tins.json` or `.tins/kit/` by hand.
- Never drive the owner's own VS Code (its bridge port is 47511); use a throwaway editor with its own `--user-data-dir` and `--extensions-dir` (port 47611).
