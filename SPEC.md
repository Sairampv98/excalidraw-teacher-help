# SPEC — excalidraw fork

The source of truth for this project. Rows are `D-n` (decisions) and `AC-n` (acceptance, each naming the test file that checks it). Format required by `.tins/kit/src/spec.mjs`:

- a decision row is `| D-n | <label> | locked | <detail> |` — the **label** cell (2nd column) is where a dependency name must appear, and the **status** cell (3rd column) must be `locked`, `open` or `superseded by D-n`;
- an acceptance row is `| AC-n | <label> | <check-file> | <detail> |` — the **check** cell (3rd column) names a file that must exist and must mention the `AC-n` id.

Wave 1 (this file) covers user items 1, 4, 5 and 8. The design that these rows implement is `docs/superpowers/specs/2026-10-20-page-document-model-design.md`.

Wave 2 (this file, rows D-12, AC-10, AC-11) covers user item 2 — content inserted while a later page is active must land on that page. Its design is `docs/superpowers/specs/2026-10-20-image-page-stamping-design.md`.

Wave 2 (this file, rows D-13, AC-13, AC-14, AC-15) covers user item 3 — the pen produced broken, segmented curves because the pointer samples the device reported between two frames were thrown away. Its design is `docs/superpowers/specs/2026-10-20-draw-performance-design.md`.

Wave 4 (this file, rows D-17, D-18, D-19, D-20, AC-23, AC-24, AC-25) covers user items 1, 2 and 5 — the right-click paste has to keep the code card, and the markdown viewer has to copy what is selected. Its design is `docs/superpowers/specs/2026-10-21-paste-and-markdown-design.md`.

Wave 4b (this file, rows D-21, D-22, D-23, AC-26, AC-27, AC-28) covers user items 3 and 4 — a selection of text can be **reformatted** into a code card or into a drawn table. Its design is `docs/superpowers/specs/2026-10-21-reformat-selection-design.md`.

Wave 4c (this file, rows D-24, D-25, D-26, AC-29, AC-30, AC-31) covers the owner's decision Q3 (2026-10-21) — a paste that does not fit the page is **offered** to the user, and the text that is left over goes back to the clipboard. Its design is `docs/superpowers/specs/2026-10-21-paste-overflow-design.md`.

Wave 6a (this file, rows D-35, D-36, D-37, D-38, AC-41, AC-42, AC-43) covers user item 9 — a saved `.excalidraw` file can be inserted into the canvas that is already open. Its design is `docs/superpowers/specs/2026-10-21-insert-document-design.md`.

Wave 6c (this file, rows D-42, D-43, D-44, D-60, D-61, D-62, D-63, AC-48, AC-49, AC-50, AC-51) covers user item 11 — a flowchart that comes alive: the current step is enlarged, the components in it animate, and the whole thing loops. The owner's decision (question 9, 2026-10-21) made it an **overlay** triggered from a **properties-panel section**, so there is no new element type and nothing is written into the document. Its design is `docs/superpowers/specs/2026-10-21-flow-animation-design.md`.

## Decisions

| id | label | status | detail |
| --- | --- | --- | --- | --- | --- |
| D-1 | page geometry | locked | `ExcalidrawPage` gains `width`, `height` and `contentScale`. 1920x1080 is the **minimum** page size; a page may only grow. Pages are laid out left-to-right by **cumulative offsets**, because the index-based `index * PAGE_GAP` formula cannot express pages of differing sizes. `PAGE_GAP` is retained. The three fields are **optional in the type** and resolved by `normalizePage` to `PAGE_WIDTH` / `PAGE_HEIGHT` / `1`, so a document written before pages carried a size (and a host that builds a page itself) keeps working; a page's rect is always at least the minimum size. `PAGE_GAP` keeps its value — the pitch between two default-sized page origins — and `PAGE_SPACING` (200) is the gap between the two page rects, so the cumulative layout reproduces the old `index * PAGE_GAP` positions exactly for default-sized pages. |
| D-2 | one scaling axis | locked | **Scale content** is the only way to get more room on a page: it divides that page's element geometry by 2, leaves the page rect alone, and its reverse (x2) undoes it. There is **no** "grow page" / "shrink page" control any more — the page bar offered both, they did the same job as the content controls, and growing a page pushed the **later** pages sideways, because the layout is positional and the later pages' rects move (the user's own fix, 2026-10-21: "just select all the existing content on the page that needs to be expanded and just scale it down"). A page's rect still grows where it must — to contain the content restored onto it (`growPagesToFitContent`, D-5) — but that is the importer's job, not a control. Implemented as the pure helper `scalePageContent` (`scene/pages.ts`), which rewrites stored geometry and touches no renderer state. |
| D-3 | scaling persists geometry | locked | Scaling rewrites the **stored** element geometry. It is NOT a render-time multiplier. Reason: the fork has already been broken once by coordinate-convention drift (the scroll-sign defect recorded in `HANDOVER.md` section 2). A render-time multiplier would spread that class of bug across the renderer, exporter, hit-testing, bounds and presenter. The scale step is 0.5 and its inverse 2, both exact in binary floating point, so a down/up round trip is lossless. Scaled: `x`, `y`, `width`, `height`, free-draw / linear `points`, `strokeWidth`, and `fontSize` for text. Not scaled: `angle`, `groupIds`, `boundElements`, `link`, `frameId` — those are references, not geometry. A text container and its bound text are both anchored, so they scale together and the binding survives. |
| D-4 | floating elements | locked | A new **optional** per-element flag `floating?: boolean` marks an element as not owned by its page's coordinate space. A floating element is excluded from _scale content_, may sit outside the page rect, and widens the camera clamp domain to the union of the page rect and the floating elements' bounding box (`getPageClampRect`, used by the editor's camera clamp). The flag is opt-in and never set automatically — an element that does not carry it does not grow one on restore. |
| D-5 | imported content | locked | After restoring a scene, any page whose element bounding box exceeds the page rect **grows the page** to contain it, so imported content is never silently unreachable. To keep specific content deliberately outside, the user marks it floating and drags it out. Both directions are reversible. A page's origin is derived from the layout and is not stored, so a page can only grow to the right and downwards: content left of / above the page's origin cannot be contained by growing the page and has to be marked floating to be reachable. |
| D-6 | document storage | locked | The document is persisted through a `DocumentStore` interface with two backends: **IndexedDB is primary** (`idb-keyval`, already a dependency) and **localStorage is the fallback** when IndexedDB is unavailable. The page index and the per-page element buckets are written as **separate records**, so a failed element write cannot lose the page list. A write failure is surfaced to the user, never swallowed. |
| D-7 | restore does not inherit local structure | locked | `restoreAppState` must not take the running app's `pages` or `currentPageId` for a file that does not define them. The local appState is a fallback for **view preferences** only (theme, sidebar, grid), never for the document's own structure. A file without `pages` restores to exactly one page, and its elements are stamped to it. The file's own pages win (`getFilePages`), and elements without a `pageId` are stamped to the file's **first** page (`restoreElements`'s `defaultPageId`), not to a hard-coded default. |
| D-8 | page operations are undoable and synced | locked | `pages` and `currentPageId` are added to `getObservedAppState`, so adding, renaming or deleting a page becomes an undoable, collab-synced operation. Today they are omitted, which is why page changes are neither. They are standalone (not element) props, so `AppStateDelta.stripStandaloneProps` keeps them out of the element delta. |
| D-9 | page list and deletion | locked | The `PageBar` page list is **virtualised** — only the visible window of rows is rendered — so a document with thousands of pages does not create thousands of DOM nodes. A **single-page delete** control is added, using the existing two-step `guardDestructive` pattern. Deleting the last remaining page leaves one empty page rather than an empty document. |
| D-10 | measured, not guessed | locked | The document is instrumented: total and per-page element counts, save latency, page-switch latency, page count, active storage backend. A lazy-hydration redesign (loading only the current page's elements into memory) is **deferred** until a real document crosses a measured threshold: save p95 > 250 ms, page-switch p95 > 120 ms, more than 50,000 elements, or more than 2,000 pages. |
| D-11 | no new dependency | locked | Wave 1 adds **no** dependency. Everything it needs is already available: `idb-keyval` (storage), the existing `files-db` binary store (images/GIFs), and the existing fractional-indexing package. |
| D-12 | insertion belongs to the current page | locked | An element inserted into the **live** scene belongs to the page the user is acting on. Neither element factory can know it — `newElement()` cannot ask the app (that would be a dependency cycle) and `restoreElements()` resolves from the **file** — so one authoritative helper (`stampCurrentPage`, `scene/pages.ts`) stamps the current page onto the elements, and **every** insertion path goes through it: draw, paste, library, chart, the app's sidebar insert (image and code card), and the two actions that create an element ("wrap selection in frame", "wrap text in container"). The stamp is applied **in place**, because callers keep a reference to the element they created and go on to mutate it (drag handles, binding, text editing). Restoring a file is the one exception and does not come through the helper (D-7). |
| D-13 | recover the dropped pointer samples | locked | A throttled pointer handler runs **once per animation frame** and sees only the **last** event of that frame, so the intermediate positions the device reported are thrown away: a free-draw stroke recorded one point per _frame_ instead of one point per _sample_, and a dropped frame rate turned the stroke into a polyline with visible corners. The samples are recovered from the event itself — `PointerEvent.getCoalescedEvents()` returns the whole batch the browser coalesced — and the free-draw branch appends **every** sample, each with its own pressure, so the recorded `pressures` array stays index-aligned with `points`. The helper is feature-detected and falls back to the single event: jsdom has no `window.PointerEvent` and older browsers lack the method. The throttle itself is unchanged, and the shape generation and its `streamline` pass are untouched. The per-frame cost of a stroke no longer grows with its length: the bounding box is tracked incrementally and the whole-scene scans run only when the element set changes, not on every frame. |
| D-14 | the offer is made on import | locked | A file that defines **no pages** of its own and whose content does not fit on one page is **offered** a split when it is opened. A file that defines its own pages has a structure its author chose, and is opened as it is. The offer is never applied automatically: the user decides. The candidate is computed in `packages/excalidraw/data/pageSplit.ts` (which wraps `paginateContentIntoPages` from `packages/excalidraw/scene/pages.ts`) and handed back by `loadSceneOrLibraryFromBlob` in `packages/excalidraw/data/blob.ts` as `pageSplit`; `loadFileToCanvas` in `packages/excalidraw/components/App.tsx` raises the offer. `loadFromBlob` is unchanged, so every other caller keeps today's behaviour. |
| D-15 | three answers: split, keep, cancel | locked | The offer is answered by one of three: **split across pages** (recommended) tiles the content, **keep on one big page** leaves the grown page the import already produces (`growPagesToFitContent` + `translateContentForPageLayout`), and **cancel** imports nothing and leaves the canvas exactly as it was. The dialog is built on the library's own `Modal` (`packages/excalidraw/components/Modal.tsx`) and driven by the promise/atom pattern of `packages/excalidraw/components/OverwriteConfirm/OverwriteConfirmState.ts`, because `Dialog` is bound to the app's `openDialog` state and cannot carry a promise. |
| D-16 | the tiling is computed once | locked | `paginateContentIntoPages` is a pure pass over the whole scene, so the candidate is computed **once**: the page count the offer shows is the number of pages the split actually produces, and the very same candidate is the one that is imported. The candidate is computed from the **restored** elements — the ones the tiling acts on — and not from the grown-and-translated ones. |
| D-17 | the armed paste is decided in the library's paste path | locked | The armed code paste is decided **inside the library's paste path**, through the library's existing `props.onPaste` hook, and the app's `window` capture-phase `paste` listener is gone. The context menu's Paste (`actionPaste`) fires **no DOM paste event** — it reads the clipboard and calls `app.pasteFromClipboard(...)` directly — so a listener only ever saw the keyboard paste and the right-click paste came out as plain text boxes. `pasteFromClipboard` is the one funnel both paths go through, so the hook covers both and there is one behaviour. The hook returns `false` to mean "handled it, stop"; the library calls `event?.preventDefault()` only **after** the hook, so the app's handler calls it itself. The pointer is still tracked with a `pointermove` listener on `window` and used for the card's placement in **both** paths — `actionPaste` builds a synthetic event whose `clientX`/`clientY` are 0. The plain-text copy on the clipboard is left alone, so pasting into another app still gets ordinary text. |
| D-18 | the armed paste needs the stashed code on the clipboard | locked | The armed paste is consumed **only** when the clipboard still holds the stashed code. The library trims the text it parses out of the clipboard, so the comparison is made on the trimmed text on both sides. If the user copied something else in the meantime, the paste is an **ordinary** paste and the armed paste is not spent — it is still waiting for a paste of that code. |
| D-19 | selecting in the markdown viewer copies | locked | Selecting text in the markdown viewer **copies it to the clipboard automatically**. The copy happens on the **mouse-up / key-up** that ends the selection, not on `selectionchange`: a clipboard write needs a transient user activation and `selectionchange` carries none, so `navigator.clipboard.writeText` would be rejected with `NotAllowedError`. A link's text is ordinary text inside the body, so it is covered by the same code. A failed write is caught and reported with the app's own toast. |
| D-20 | only a selection inside the markdown body is copied | locked | Only a selection that lies **wholly inside** the markdown body is copied: both ends of the range have to be inside the body. A selection that reaches out of the viewer is left to the browser. |
| D-21 | the library offers the reformat, the app does it | locked | The library gains an `onReformatSelection` prop and one canvas context-menu entry, **"Reformat as..."** (`actionReformatSelection`). The entry appears **only** when the selection holds at least one text element, and only when the host app handles the prop at all. The library does **not** reformat anything itself: a syntax-highlighted code card needs the host app's own highlighter (`shiki` is the app's dependency, not the library's), so the library owns the _offer_ and hands the selection over — the same extension pattern `onPaste`, `onDuplicate` and `onLibraryChange` already use. The two formats are offered by **one** action over a selection, not by two separate actions: the owner's decision. |
| D-22 | the code-card reformat replaces the selection | locked | The code-card reformat reuses the app's own `insertCodeIntoScene(api, rawCode, { fileName, language, at })`, so the result is the very same card the sidebar's Insert button builds — a dark rectangle with the code on it as real, selectable text. The card is placed at the **selection's own top-left**, measured with the library's own `getCommonBounds`, never with a re-derived formula. The **original text elements are deleted**: the reformatted content _replaces_ the selection. A selection carries no filename, so there is no language to read — the app's plain-text language (`text`, the one `languageFor` gives a `.txt` document) is used, which is the language the app's own plain-text inserts use. |
| D-23 | the table is drawn behind ordinary text cells | locked | The table reformat recovers the cells from the lines of the selection: a markdown row (starts and ends with ` | `) is split on ` | `, any other line is split on a **tab** (what a table copied from a spreadsheet or a PDF puts between its cells), and the markdown **separator row** (all dashes and colons) is **dropped** — it is a rule, not a row of the table. The cells are laid out on a grid — a column is as wide as its widest cell, with a floor and a ceiling — and the table is **drawn**: one rectangle per cell, **behind** ordinary, **selectable** text elements (never an image, never a locked group), because the owner asked for the cells to stay selectable. The table starts at the selection's own top-left, measured the same way as the code card. |
| D-24 | the paste that does not fit is offered | locked | A paste that does not fit the **current page** raises an **offer** — it is never resolved automatically. The bound is the current page's rect (`getCurrentPageRect`), **not** the viewport: the viewport is what the camera happens to show, the page is what the camera is clamped to, and a paste that fits the viewport but hangs off the page is exactly the failure the owner reported. The offer's three answers are the owner's own — **discard remaining text**, **place all text on this page**, **place text on multiple pages** — and dismissing the offer without a choice is the first answer _without_ the clipboard write: what fits is placed and the rest is left in the clipboard. The offer is a promise/atom dialog beside the page-split offer (`PasteOverflowDialog/`, mounted in `LayerUI.tsx`, awaited in the paste path), exactly like the import offer (D-14). It is raised only when the pages system is on: without it the camera is not clamped to a page, so nothing can become unreachable. The pasted text is placed **inside** the page — a page grows to the right and downwards only (D-5), so a text that hangs over the page's left or top edge is nudged into the page, which is the only placement the camera can reach. |
| D-25 | the fit is decided per line | locked | The text that does not fit is decided **per line**: a line whose text element lies **entirely inside** the page's rect fits, and a line that **straddles** the edge overflows — half a line hanging over the edge is not readable, and the camera cannot reach it. The measurement is the library's own: the element's bounding box (`getCommonBounds`) against the page's rect (`isElementInsidePageRect` / `countElementsInsidePageRect`, `scene/pages.ts`), never a re-derived formula. The first line that does not fit, and everything after it, overflows. Splitting the text into chunks for the "across pages" answer uses the same rule: a chunk is the longest run of lines that fits the page, and the next chunk starts a new page. |
| D-26 | the leftover goes back to the clipboard | locked | Whatever is left over is **written back to the clipboard**, so the user can paste the rest somewhere else. The clipboard is the user's, and nothing is thrown away silently: the "discard remaining text" answer places only the part that fits and puts the rest on the clipboard, while the two answers that place everything leave nothing over and write nothing. The write happens on the answer the user gave — a click carries the transient user activation a clipboard write needs — and a blocked clipboard is reported with the app's toast, not thrown. |
| D-27 | the page-relative offset is signed | locked | The page-relative camera offset is a **signed** ratio, not a 0..1 fraction: it is how far the page's near edge is behind the viewport's near edge, measured in page widths. It is **negative** when the viewport is wider than the page and the camera has centred the page, and that negative value is what makes the mirrored window show the same slice. The regression: the offset was clamped to `0..1`, so the negative anchor of a centred page was thrown away and turned into "the page's near edge is at the viewport's near edge" — a different camera, a third of a page away from the editor's. The library's own page-camera test now checks the anchor against the **renderer's** slack in front of the page (zero when the page's near edge is flush with the viewport's near edge, negative when the page is centred with slack in front of it) instead of against the old clamped fraction. |
| D-28 | the offset is bounded above only | locked | The offset is bounded **above** at 1 and is **not** bounded below. The camera clamp guarantees the upper bound; the lower end is unbounded (a narrow, tall page in a wide window), so a lower clamp would throw away real geometry. |
| D-29 | the presenter test anchors on the library's page rect | locked | The presenter camera test uses the **library's** `getCurrentPageRect`, not a re-derived page rect. The fork's page layout is cumulative and each page is as big as its own content, so a fixed-pitch re-derivation silently stops being the truth — and it is exactly what hid the presenter's drift. |
| D-30 | the presenter's zoom floor is the **page's own** fit zoom | locked | `resolvePresenterCamera` clamps the mirrored zoom from below by the zoom at which the whole page fits the presenter's window. That floor is the fit zoom of **the page being mirrored**, not of the default page size: a legacy file's page is grown to hold the whole board, so its fit zoom is far smaller than the default's, and the default's floor would force the mirrored window to zoom **in** past the editor's own — showing a tenth of the board at ten times the size. `getFitPageZoom` already takes the page's size as arguments, so the fix is to pass the page rect's own width and height. |
| D-35 | inserting a document is an **explicit action** | locked | Inserting a document is an **explicit action** — "File > Insert document..." — and not a question asked on every open. Opening a file keeps **replacing** the canvas: `loadFileToCanvas` syncs the file's elements with `replaceFiles: true`, so the document that was open is gone. A modal on every open would ask a question the user almost never wants to answer, and the owner's wording is an action ("insert ... into another opened canvas"), not a change to what "open" means. The action is **not offered when the canvas is empty** — inserting into an empty canvas is exactly what "open" does, and offering both would be noise — and it is switched on by the host app through `UIOptions.canvasActions.insertDocument`, like every other canvas action. |
| D-36 | the inserted content is flattened onto the current page | locked | The inserted content is **flattened onto the current page** and stamped with it by the same authoritative helper every other insertion path uses (`stampCurrentPage`, D-12). The other document's **page structure is not merged**: interleaving two page layouts is a different feature, and the owner asked for the _drawing_ to come across. The file is read **without** the import path's page logic — `loadSceneOrLibraryFromBlob` grows the page to contain the content and translates the content to follow the grown page, which is right for an import and wrong for an insertion into a document that already exists — so the inserted content keeps its own coordinates and is only moved by the placement (D-38). |
| D-37 | the inserted binary files get fresh ids | locked | The inserted content's **binary files are given fresh ids** and the elements' `fileId`s are rewritten to match, so an id clash with this document's file store cannot silently change an image. The inserted **elements** get ids of their own for the same reason: an element id that is already in this document would collapse the two into one. Both remappings happen in `scene/insertDocument.ts`, and the fresh file id is checked against the ids already in this document's file store, so it cannot collide with one of them either. |
| D-38 | the inserted content is placed beside what is already on the page | locked | The inserted content is placed **beside** what is already on the page — to the **right** of it, one `PAGE_SPACING` away — and the page **grows** to contain it (`growPagesToFitContent` + `translateContentForPageLayout`, the same primitives the import path uses). The placement is measured with the library's own `getCommonBounds`, never with a re-derived formula, and it is measured against the page's **content** — the elements of that page that are neither deleted nor floating, the same set the page model calls the page's content. On a page with no content the inserted content lands on the **page's origin**. What arrived is **selected**, so the user can see it and move it. |
| D-42 | the animation is a properties-panel section, played as an overlay | locked | The owner's decision (2026-10-21, question 9): the animation is configured in a **section of the properties panel** and played as an **overlay** over the canvas. It is **not** a panel element: there is no new element type, the user's flowchart stays ordinary shapes and arrows, and playing the animation writes **nothing** into the document. The section is a `<fieldset>` + `<legend>`, like the Layers / Align / Actions sections around it, and it appears when the selection holds **two or more** elements, because a one-element selection has no flow. |
| D-43 | the step order comes from the arrows, with reading order as the tie-break | locked | The **steps are the selected elements**, ordered by the **arrows** between them: an arrow that is in the selection and whose `startBinding` and `endBinding` name two of the selected shapes says "these two are consecutive", and the order is a **topological sort** over those edges. Where the arrows do not decide, the tie is broken by the **reading order** (D-61). The resolver is a **pure function** in `packages/excalidraw/scene/flowOrder.ts`, so the order can be tested without a canvas. |
| D-44 | the overlay does not replace the canvas | locked | The overlay is a **DOM layer over the canvas**, exactly like the animated-image overlay: the canvas keeps drawing the flowchart as usual and the overlay only adds the **focus treatment** on top. Its position is computed with the library's own **`sceneCoordsToViewportCoords`** — the oracle (D-34) — and never with a re-derived formula, and it is not a copy of `animatedImageTransform`. The test asserts it the way the animated-image overlay's test does: through the oracle and the produced transform string, parsed and applied with plain matrix maths. |
| D-60 | a step is a container, not a shape | locked | `getTargetElements` folds the bound text into the selection, so a labelled box arrives as **two** `targetElements` entries. A step is therefore the **container** and its label together, and the resolver **dedupes on the container** rather than trusting `targetElements.length`. The step's bounds are the **union** of the container's and its label's, measured with the library's own `getCommonBounds`, and that union is what the focus treatment scales about. |
| D-61 | the reading order is a row band, then left to right | locked | The reading order is a **row band** and then left to right. The band test is an **overlap**, not a tolerance: two shapes are in the same band when their vertical spans intersect, so there is no magic pixel. A shape that lies entirely below another is in a later band, and a shape that straddles two bands joins the band it overlaps most. The bands themselves are ordered top to bottom. **No reading-order helper existed anywhere in the repository** — this one is written here, in `packages/excalidraw/scene/flowOrder.ts`. |
| D-62 | a cycle is broken, not refused | locked | The owner's own words are "this entire thing is in a loop", so a flowchart whose arrows form a cycle is **expected**, not an error. `dagre.layout()` does not tolerate a cycle, so the cycle is found with **`graphlib.alg.findCycles(g)`** and its **back-edge is dropped**, and the rest is laid out. In the **step order** the cycle is broken at its **lowest-reading-order member** and the flow carries on from there. The dropped edge is the loop, and the animation repeats that step. |
| D-63 | the clock is the AnimationController, never React state | locked | A `setState` per frame would re-render the whole Excalidraw app sixty times a second, so the per-frame clock is the library's own **`AnimationController`** (`packages/excalidraw/renderer/animation.ts`). The section and the overlay talk through a **jotai atom** (the `PageSplitState.ts` pattern), so nothing about the animation is written into `appState` — and therefore nothing about it reaches the saved document. Only the **step** that is focused changes, and it changes once per step, not once per frame. |
| D-70 | the clipboard comparison normalises the line endings on **both** sides | locked | The clipboard on Windows hands the text back with **CRLF**, while the code that was stashed has **LF**: `navigator.clipboard.writeText` writes what it is given and the clipboard normalises it on the way in. The comparison was byte-exact, so on Windows the armed paste was **always** declined and the code always arrived as plain text — a row of bordered text boxes, which is what the owner reported. The fix normalises CRLF to LF and a lone CR to LF on **both** sides before comparing, and **nothing else** about the comparison changes: a clipboard that holds different code is still an ordinary paste. It is deliberately **not** "compare the first line" and **not** "compare a prefix" — both would paste the wrong code when the clipboard holds something else. |
| D-71 | the armed paste survives the sidebar closing | locked | Clicking the canvas **closes** the sidebar, which unmounts the document viewer, and the viewer's cleanup cancelled the armed paste — so the owner's own sequence (Copy code, click the canvas, paste) had nothing armed by the time the paste arrived. The unmount cancel was redundant protection: the guard that matters already exists and is better, **`clipboardHoldsCode`**, which refuses a stale arm because a clipboard that no longer holds the code must produce an ordinary paste. The cancel therefore stays for the cases that really are a change of mind — the reader opens a **different** document (the `[entry]` change), the paste is consumed, and the reader goes **back to the file list** (an explicit cancel) — and it no longer runs on unmount. |
| D-72 | the pointer-position veto belongs to the **synthetic** paste only | locked | `lastViewportPosition` holds wherever the pointer last was, and right after clicking **Copy code** that is a point **inside the sidebar**, so the element-under-the-cursor check vetoed the paste and the keyboard paste did nothing at all. For the context menu's paste the pointer is meaningful — the user right-clicked there; for a keyboard paste there is no pointer at all. The veto therefore applies to the paste event the **library creates** (`createPasteEvent`), which is marked as such; the browser's own paste event is trusted and is never vetoed. ### Also changed, deliberately without an acceptance row

These are recorded apart from the main table so that the numbering of the waves in flight does not shift underneath them. They are **locked**.

The first two are the owner's explicit approvals of two things that would otherwise have needed a new dependency. | Row | The decision | Status | Detail |

| D-33 | a panel's live/poster state is `posterMode`, not `locked` | locked | The base element **already has** a `locked: boolean` (`packages/element/src/types.ts:93`), and it means "this element is immutable / not freely selectable" — it is read at `typeChecks.ts:166,183,236` and at `selection.ts:54` (`element.locked \|\| isBoundToContainer(element)`). | D-68 | Cropping a poster is **app-level new UI** | locked | The library's existing crop is an **in-place crop mode on an image element** (`croppingElementId` in `AppState`, the handlers at `packages/excalidraw/components/App.tsx:10512` and `:13013`, and the `crop` field on `ExcalidrawImageElement`). | D-69 | the gate runs its read-only steps in parallel and sizes vitest from the free memory | locked | The gate's four steps are **not** equally heavy. `tsc`, `eslint` and `prettier` only **read** files and do not depend on each other, so running them one after another wastes the machine: measured on 2026-10-21, they took 32.4 s, 89.2 s and 6.8 s — 128 s of the 374 s the whole gate took. | D-79 | the active tab is the file, even when the window is in the background | locked | The commonest moment of the whole feature is the one the active editor cannot see: the teacher teaches from the editor, then **switches to the browser** to show the canvas - and the editor window loses the focus.
